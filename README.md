# MHRD Analytics Dashboard

A Django + Django REST Framework analytics dashboard over a **synthetic India-wide education dataset** — modelled on the kind of drill-down view a ministry dashboard needs: states, schemes, initiatives, budgets and outcomes from 2023 to 2025.

**Live:** https://mhrd-dashboard.onrender.com
**Stack:** Django 4.2 · Django REST Framework · SQLite (local) / PostgreSQL via `DATABASE_URL` · WhiteNoise · Gunicorn · Render

> The demo runs on Render's free tier, so the first request after a period of inactivity can take ~30–40 seconds while the instance boots. The data itself is synthetic — see [Data](#data) below.

---

## What it does

- **Overview** — national KPI cards (schools impacted, students reached, scholarships awarded, budget utilised) with year-over-year deltas.
- **Trends** — monthly time series per scheme, filterable by year, rendered client-side.
- **Impact map** — a real India state geography, shaded by initiative activity, with click-through to a state's detail page.
- **States** — one page per state: its initiatives grouped by scheme, progress bars, budget split.
- **Schemes** — one page per scheme (Samagra Shiksha, PM SHRI Schools, PM POSHAN, PM eVIDYA, SWAYAM, DIKSHA, and others): national reach, state coverage, comparison.
- **Compare** — put two states or two schemes side by side on shared metrics.
- **Search** — a single endpoint across states, schemes and initiatives.
- **Reports** — create a report from chosen filters, poll its status, download it; every state and scheme page also renders a printable A4 view and a PDF.
- **CSV export** — the full filtered dataset, not a screenshot of it.

## Architecture

```
mhrd_dashboard/          Django project — settings, URLs, WSGI/ASGI
dashboard/
  models.py              State, Scheme, Initiative, Report
  data.py                synthetic dataset generator (deterministic seed)
  api.py                 DRF viewsets for states / schemes / initiatives
  views.py               HTML pages + JSON endpoints + CSV/PDF export
  serializers.py         DRF serializers
  management/commands/
    import_demo_data.py  loads the synthetic dataset into the database
  templates/             server-rendered pages (overview, detail, compare, print)
static/                  dashboard JS (charts, map, filters), CSS, India geo JSON
render.yaml              one-click Render blueprint (build + start commands)
```

Design decisions worth calling out:

- **Server-rendered pages, JSON on the side.** Browsers get HTML with data already in place; the JS layer fetches `/api/v1/*` only for charts, filters and the map. No blank first paint.
- **Synthetic data lives in code, not a fixture.** `dashboard/data.py` generates the dataset with a fixed seed, so `import_demo_data` produces the same numbers on every machine — the dashboard is reproducible in a fresh clone.
- **SQLite fallback on Render.** If `DATABASE_URL` is absent or stale, settings fall back to SQLite rather than failing the boot, and the build step logs a migration warning instead of aborting.
- **Real geography, fake numbers.** The map uses actual India state boundaries and an Esri light-gray basemap; the metrics drawn on top are explicitly synthetic.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/v1/health` | Health check (used by Render) |
| GET | `/api/v1/meta` | Years, schemes and states available |
| GET | `/api/v1/kpis` | National KPI cards, optional `?year=` |
| GET | `/api/v1/trends` | Monthly trends, `?year=&scheme=` |
| GET | `/api/v1/map` | Per-state map values |
| GET | `/api/v1/schemes` | Scheme list with summary metrics |
| GET | `/api/v1/schemes/<slug>/kpis` | One scheme's KPIs |
| GET | `/api/v1/search?q=` | Search states, schemes, initiatives |
| GET | `/api/v1/compare/trends` | Side-by-side trends |
| GET | `/api/v1/exports/data.csv` | CSV export of the filtered dataset |
| POST | `/api/v1/reports` | Create a report from params |
| GET | `/api/v1/reports/<id>` | Poll report status / fetch it |
| GET | `/api/v1/db/states/` | DRF viewset — states |
| GET | `/api/v1/db/schemes/` | DRF viewset — schemes |
| GET | `/api/v1/db/initiatives/` | DRF viewset — initiatives |

## Run locally

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python manage.py migrate
python manage.py import_demo_data
python manage.py runserver
```

Open http://127.0.0.1:8000/. No environment variables are required for local development; set `DATABASE_URL` to point at Postgres instead of the SQLite default.

## Deploy

`render.yaml` is a working Render blueprint: it installs requirements, collects static files with WhiteNoise, migrates, seeds nothing automatically, and starts Gunicorn. Set `SECRET_KEY` (generated by the blueprint) and, if you have one, `DATABASE_URL`.

After the first deploy run the seed command once, either from the Render shell or by adding it to the build command:

```bash
python manage.py import_demo_data
```

## Data

Every number in this project is **synthetic** and generated in `dashboard/data.py` for demonstration. It is not sourced from, or representative of, real government reporting. The state names and geography are real; the schemes are real programme names used as labels for fake aggregates. Don't cite these figures anywhere.

## What I'd do next

- Swap the synthetic generator for a real ingestion path (CSV/Excel upload with `django-import-export`, already in the requirements).
- Replace the polling report stub with a background worker (Celery or RQ) so PDF generation stops blocking a request.
- Cache the `/api/v1/kpis` and `/api/v1/map` payloads — they change once per import.
- Add DRF auth for the write endpoints (`/api/v1/reports` is currently open).
